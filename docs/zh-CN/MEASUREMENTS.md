## 1. 链路硬约束（决定设计，不是调参能改的）

| # | 结论 | 怎么得到的 | 对设计的影响 |
|---|---|---|---|
| 1 | **游戏独占全屏会把 HDMI 输出锁到 60 Hz** | 桌面 120 Hz、进游戏后采集卡只出 60 帧 | 采样率上限 60 fps，控制策略必须按「低采样 + 高延迟」设计 |
| 2 | 采集卡有 1–5 帧固有信号延迟，且**分辨率不对齐会再 +1~2 帧** | 切换采集分辨率对比同一场景的响应时间 | `capture.width/height` 必须与游戏原生分辨率一致 |
| 3 | 推理**不是**瓶颈 | 320×320 导出 p50 4–5 ms（见 §3） | 优化重点放在延迟补偿而不是模型加速 |
| 4 | 串口**不是**瓶颈 | 921600 bps 下 9 字节帧 ≈ 9400 帧/秒，实测无积压 | 报告率可以做到 1000 Hz |
| 5 | 端到端延迟在 30 ms 量级（≈2 帧） | 闭环在线辨识：`Δe_k + u_{k-m}` 残差最小化，m≈8 tick @240 Hz | 必须做延迟补偿；控制增益上限被延迟锁死 |
| 6 | 60 fps 下「甩枪 + 稳定」的物理极限约 10 帧（167 ms） | 仿真台 + 实测一致 | 提帧率是唯一质变路径，其余都是逼近这个极限 |

## 2. 为什么不能用「高增益 PID」

在延迟 D 帧的积分型被控对象上，纯比例控制的稳定条件是 `kp·D < 2` 左右；
60 fps、D≈2 时，可视化手感要求 `kp > 1`，于是必然进入极限环：准星在目标两侧来回扫。

复现实验（`tests/test_control.py::test_sim_survives_a_wrong_apply_window`）：

| 控制器以为的「命令生效窗口」 | 真实延迟 33 ms 时的跟踪误差 RMS | 命中窗口占比 |
|---|---|---|
| 2.5 ms | **304 px** | **1 %** |
| 10 ms | 10.7 px | 99 % |
| 16.5 ms（正确值） | 11.7 px | 99 % |

结论：**延迟估计每错一倍，有效环路增益就错一倍。** 这就是为什么
`control/latency.py` 有物理下限（≥1.2 帧）与三重拒绝条件，而不是「估到什么用什么」。

## 3. 推理延迟（本机 CoreML，2560×1600 输入帧，`aim2 models bench`）

| 模型输出格式 | 输入 | p50 | p95 | 60 fps 预算余量 |
|---|---|---|---|---|
| YOLOv8 `[1,9,2100]` | 320×320 | 4.1 ms | 7.9 ms | +8.8 ms |
| 端到端 `[1,300,6]` | 320×320 | 5.0 ms | 6.3 ms | +10.4 ms |
| YOLOv5 `[1,25200,7]` | 640×640 | 7.4 ms | 8.2 ms | +8.5 ms |
| 端到端 `[1,300,6]` | 640×640 | 16.6 ms | 20.6 ms | **−3.9 ms（掉帧）** |
| 端到端 `[1,300,6]` | 416×416 | 13.9 ms | 14.3 ms | +2.4 ms（发热即超） |

60 fps 的预算是 16.7 ms/帧。**只有 320 级导出留有余量**；640 会开始丢帧。

## 4. 控制律对照（闭环仿真：33 ms 延迟、2.5 px 检测噪声、60 fps 采集）

对照组 `legacy` = 经典「对延迟误差做 PID」，强制 60 Hz 控制、无跟踪（`dma/control/legacy_pid.py`）。

| 场景 | 指标 | legacy | 本实现 |
|---|---|---|---|
| 中距横扫 | RMS / 命中窗口 | 22.5 px / 53 % | **10.6 px / 99 %** |
| 远距横扫 | RMS / 命中窗口 | 60.3 px / 34 % | **45.1 px / 96 %** |
| 远距横扫 | 恢复时间 | 0.27 s | **0.12 s** |
| 甩枪（500 px 瞬移） | 恢复 / 抖动 | 0.16 s / 10.5 px | **0.09 s / 3.1 px** |
| 露头（反复消失） | 首次捕获 | 0.27 s | **0.14 s** |
| 近静止抖动 | 输出抖动 | 3.8 px | **1.9 px** |

复现：`aim2 sim --compare` / 回归门禁：`aim2 bench`（任一指标退化即返回非零）。

## 5. 资源与散热（同一台无风扇笔记本，320×320 端到端模型）

| 配置 | 单帧延迟 | 单帧 CPU 时间 | 持续 CPU 占用 |
|---|---|---|---|
| CoreML，`intra_threads=2` | 6.32 ms | 13.47 ms | **213 %** |
| CoreML，`intra_threads=1` | 6.40 ms | 7.17 ms | **112 %** |
| CPU，1 线程 | 14.57 ms | 16.93 ms | 116 % |

结论：**多线程不缩短延迟，只多烧一个核。** 无风扇机器上这是降频的直接原因。
界面预览同理：30 fps 全分辨率平滑缩放改为「先缩后贴 + 可配帧率」后，
界面 + 引擎合计从约 3/4 核降到约 1/2 核。

## 6. 身体类模型的头点

只有身体类的模型（`st` / `body`）没有 `head`，锁头只能用
`aim_point_y = box.y1 + head_ratio · box.h`：

- 必须**现场用实时画面里的红十字标定**，不同分辨率/视角比例不同；
- 常见区间 0.08–0.15；偏大打到脖子，偏小会落空；
- 这是模型能力的限制，不是控制参数能补偿的。

## 7. 验收标准

一次有敌人的对局，退出时的会话体检应满足：

| 指标 | 合格线 | 说明 |
|---|---|---|
| `误差 p50` | < 8 px | 准星与瞄准点的日常距离 |
| `误差 p95` | < 15 px | 甩枪/换靶后的收敛质量 |
| `延迟` | 25–60 ms 且 conf > 0.3 | 低于 20 ms 在物理上不可能 |
| 开火原因 | `off-target` 不应占 90 % 以上 | 否则说明没锁住或半径过紧 |
